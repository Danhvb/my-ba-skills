# Requirements Elicitation Best Practices Checklist

## Pre-Elicitation Preparation

### Research & Planning
- [ ] Research the business domain and industry
- [ ] Review existing documentation (if available)
- [ ] Understand organizational structure
- [ ] Identify key stakeholders and their roles
- [ ] Research competitors and industry best practices
- [ ] Prepare initial questions based on project objectives
- [ ] Set up collaboration tools (Lark, Notion, Figma)

### Stakeholder Identification
- [ ] Create stakeholder matrix (power/interest grid)
- [ ] Identify primary stakeholders (decision makers)
- [ ] Identify secondary stakeholders (influencers)
- [ ] Identify end users
- [ ] Identify subject matter experts (SMEs)
- [ ] Identify technical stakeholders
- [ ] Identify compliance/legal stakeholders (if applicable)

### Logistics
- [ ] Schedule elicitation sessions with adequate time
- [ ] Send calendar invites with clear objectives
- [ ] Share pre-read materials 2-3 days in advance
- [ ] Confirm attendance 24 hours before session
- [ ] Prepare recording tools (with permission)
- [ ] Set up virtual meeting room or book physical space
- [ ] Prepare templates and worksheets

---

## During Elicitation

### Interview Best Practices
- [ ] Start with introduction and set expectations
- [ ] Request permission to record
- [ ] Use open-ended questions
- [ ] Listen actively (80/20 rule - listen 80%, talk 20%)
- [ ] Take detailed notes
- [ ] Ask "why" to understand root causes
- [ ] Probe for specifics on vague statements
- [ ] Watch for non-verbal cues
- [ ] Paraphrase to confirm understanding
- [ ] Capture exact terminology used by stakeholders
- [ ] Note assumptions and constraints
- [ ] Identify dependencies
- [ ] Allow silence - don't rush to fill gaps
- [ ] Summarize key points before ending
- [ ] Confirm next steps

### Workshop Facilitation
- [ ] Start on time
- [ ] Review objectives and agenda
- [ ] Set ground rules
- [ ] Ensure all voices are heard
- [ ] Keep discussions focused
- [ ] Use visual aids (whiteboards, Figma, Miro)
- [ ] Capture ideas without judgment during brainstorming
- [ ] Use parking lot for off-topic items
- [ ] Facilitate consensus on conflicts
- [ ] Use time-boxing for activities
- [ ] Summarize decisions and action items
- [ ] End on time
- [ ] Thank participants

### Documentation
- [ ] Document requirements in real-time
- [ ] Use consistent format and terminology
- [ ] Capture rationale for requirements
- [ ] Note source of each requirement
- [ ] Document assumptions explicitly
- [ ] Record constraints and dependencies
- [ ] Capture business rules
- [ ] Note open questions
- [ ] Take screenshots of diagrams/whiteboard
- [ ] Record decisions made

## Question Techniques

### 5W1H Framework
- [ ] **Who**: Who will use this? Who is impacted?
- [ ] **What**: What needs to be accomplished? What are the inputs/outputs?
- [ ] **When**: When does this happen? What's the frequency?
- [ ] **Where**: Where does this occur? What systems are involved?
- [ ] **Why**: Why is this needed? What's the business value?
- [ ] **How**: How is it done today? How should it work?

### Probing Questions
- [ ] "Can you give me an example?"
- [ ] "Can you walk me through that process?"
- [ ] "What happens if...?" (edge cases)
- [ ] "Why is that important?"
- [ ] "How often does this occur?"
- [ ] "What would happen if we didn't do this?"
- [ ] "What's the impact of this issue?"
- [ ] "Who else should I talk to about this?"

### Clarifying Questions
- [ ] "When you say [term], what exactly do you mean?"
- [ ] "Can you clarify what you mean by 'real-time'?"
- [ ] "What does success look like for this?"
- [ ] "What are the acceptance criteria?"
- [ ] "How will you measure this?"

### Challenging Assumptions
- [ ] "What makes you think that?"
- [ ] "Is that always true?"
- [ ] "What if we approached it differently?"
- [ ] "What are the alternatives?"
- [ ] "What's the worst that could happen?"

## Requirements Quality Checks

### Clarity
- [ ] Requirement is written in clear, simple language
- [ ] No ambiguous terms (e.g., "user-friendly", "fast", "easy")
- [ ] Technical jargon is defined
- [ ] Requirement is understandable to all stakeholders

### Completeness
- [ ] All necessary information is included
- [ ] Inputs and outputs are defined
- [ ] Success criteria are specified
- [ ] Edge cases are addressed
- [ ] Exceptions are documented

### Consistency
- [ ] Requirement doesn't conflict with other requirements
- [ ] Terminology is consistent across requirements
- [ ] Requirement aligns with business objectives

### Testability
- [ ] Requirement can be verified through testing
- [ ] Acceptance criteria are measurable
- [ ] Success can be objectively determined

### Traceability
- [ ] Requirement is linked to business need
- [ ] Source is documented (stakeholder, document, workshop)
- [ ] Requirement has unique identifier

### Feasibility
- [ ] Requirement is technically feasible
- [ ] Requirement is achievable within constraints
- [ ] Dependencies are identified

## Post-Elicitation Activities

### Immediate Follow-up (Within 24-48 hours)
- [ ] Clean up and organize notes
- [ ] Create structured requirements document
- [ ] Identify gaps and open questions
- [ ] Share notes with participants for validation
- [ ] Send thank you notes to participants
- [ ] Update requirements register
- [ ] Update stakeholder matrix

### Analysis
- [ ] Categorize requirements (functional, non-functional, data, integration)
- [ ] Identify dependencies between requirements
- [ ] Analyze for conflicts or inconsistencies
- [ ] Group related requirements
- [ ] Identify requirements that need further elaboration
- [ ] Assess completeness - are there gaps?

### Validation
- [ ] Review requirements with stakeholders
- [ ] Confirm understanding is correct
- [ ] Resolve ambiguities
- [ ] Get stakeholder sign-off on requirements
- [ ] Update based on feedback

### Prioritization
- [ ] Apply prioritization framework (MoSCoW, RICE)
- [ ] Validate priorities with stakeholders
- [ ] Document rationale for priorities
- [ ] Identify MVP scope

### Documentation
- [ ] Update BRD/FRS with new requirements
- [ ] Create or update process maps
- [ ] Document business rules
- [ ] Update traceability matrix
- [ ] Version control all documents

## Common Pitfalls to Avoid

### Communication Pitfalls
- [ ] ❌ Avoid: Assuming you understand without confirming
- [ ] ✅ Do: Paraphrase and confirm understanding
- [ ] ❌ Avoid: Using technical jargon with business stakeholders
- [ ] ✅ Do: Use business language and explain technical terms
- [ ] ❌ Avoid: Interrupting stakeholders
- [ ] ✅ Do: Let them finish, then ask clarifying questions

### Requirements Pitfalls
- [ ] ❌ Avoid: Accepting vague requirements ("system should be fast")
- [ ] ✅ Do: Push for specific, measurable criteria ("page load < 3 seconds")
- [ ] ❌ Avoid: Jumping to solutions before understanding problem
- [ ] ✅ Do: Focus on "what" and "why" before "how"
- [ ] ❌ Avoid: Ignoring non-functional requirements
- [ ] ✅ Do: Explicitly ask about performance, security, usability, etc.

### Process Pitfalls
- [ ] ❌ Avoid: Skipping stakeholder validation
- [ ] ✅ Do: Always validate requirements with stakeholders
- [ ] ❌ Avoid: Documenting requirements weeks after elicitation
- [ ] ✅ Do: Document immediately while fresh in memory
- [ ] ❌ Avoid: Talking to only one stakeholder
- [ ] ✅ Do: Get multiple perspectives to avoid bias

## Success Metrics

Track these metrics to improve your elicitation effectiveness:

- [ ] **Coverage**: % of stakeholders interviewed
- [ ] **Validation Rate**: % of requirements validated by stakeholders
- [ ] **Change Rate**: % of requirements that change after initial elicitation
- [ ] **Defect Rate**: # of defects traced to poor requirements
- [ ] **Stakeholder Satisfaction**: Feedback on elicitation process
- [ ] **Time to Document**: Time from elicitation to documented requirements
- [ ] **Rework**: # of requirements requiring significant rework
